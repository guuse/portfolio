A cloud-agnostic Kubernetes hosting platform

The platform our client projects run on: eight clusters, one way of working.

Every client used to get a slightly different setup. I designed one platform instead: the same building blocks on AWS or Azure, the same pipelines, the same monitoring. It now runs eight clusters, from small to large, in the Netherlands and abroad, including Japan. The biggest runs more than 1,500 pods. New apps get production and acceptance environments, TLS, logging and dashboards on day one, without anyone touching the cluster.

afoundation

The foundation

Terraform modules for every building block, AWS first and Azure where the client lives.

  • EKS on a dual-stack (IPv4 and IPv6) network across three availability zones, with Aurora databases, Redis, OpenSearch, shared EFS storage and a bastion as ready-made modules.
  • Nodes scale with load through Karpenter, so the cluster grows and shrinks on its own.
  • Traffic: a Network Load Balancer with fixed IPs → ingress-nginx on every node (proxy protocol, HSTS) → the apps, with certificates by cert-manager.
  • Rancher to manage the whole fleet of clusters from one place.

bdelivery

App delivery: GitOps with Argo CD

Nobody edits the cluster by hand. A commit becomes a running release through git alone.

  • A root app-of-apps manages everything; Argo CD projects act as guardrails per team or client.
  • Every app gets production and acceptance: production follows the newest stable release, acceptance the newest release candidate. Builds from main never deploy.
  • CI builds immutable version tags; Argo CD Image Updater commits the new tag back to git, and Argo CD syncs.
  • Onboarding a conventional repo is adding a GitHub topic: an ApplicationSet creates both environments.

cinfra

Infrastructure delivery: Pulumi, policy first

Infrastructure changes go through the same kind of pipeline as app code, with stricter gates.

  • Pulumi in Python, one independent state per concern, each with its own foundation.
  • Policy first: a mandatory CrossGuard policy pack means a resource that breaks a rule can’t even be previewed, let alone applied.
  • Tested: the logic lives in importable modules, and resource shapes are tested with Pulumi mocks.
  • The pipeline is the only writer to production. Apply re-plans against fresh state and refuses anything destructive the reviewers didn’t approve (a fail-closed drift gate).
  • No static keys: GitHub OIDC into short-lived cloud roles, on self-hosted runners in the cluster. The deploy role can never widen its own permissions.
  • Reusable GitHub Actions for preview, deploy and drift, shared by every infrastructure repo. A daily drift check reports to Slack.

dlogs

Logging pipeline

Every log line from every pod, searchable in Grafana, stored encrypted.

  • Alloy runs on every node; Loki and its caches run on a dedicated platform node pool.
  • Logs land in encrypted object storage. Retention (90 days) is owned by Loki’s compactor, never by bucket lifecycle rules, because those would corrupt queries.
  • Exactly one service account can reach the bucket, through workload identity.

eedge

Multi-region: Europe and Tokyo

One platform, closer to users in Asia and Oceania.

  • A second cluster in Asia Pacific (Tokyo) runs next to the European one.
  • CloudFront routes by path and region and caches at the edge; dynamic requests go to the nearest cluster.
  • A small resource syncer we built (a Kubernetes CronJob) keeps chosen Deployments, ConfigMaps and Secrets in Tokyo in step with the main cluster, so there’s still one place to make changes.

freliability

Reliability

Planned, not urgent.

  • Disaster recovery with Velero on AWS and Azure: cluster resources and volume snapshots, backed up and restorable.
  • A supported-services lifecycle with published end-of-support dates per version of databases, search and ingress, so upgrades are planned instead of urgent.

goperate

Operating it: a CLI that knows every environment

We built a small Python CLI so nobody needs a wiki page to get in.

  • SSO login with an admin or read-only role, per environment.
  • A bastion shell without opening ports, policy-enforced previews, and bootstrapping a new environment’s foundation.
  • It deliberately has no apply: only the pipeline changes production.

→timeline

How it grew

  1. 2022

    A first standardised hosting cluster on AWS EKS, built from Terraform modules and managed with Rancher.

  2. then

    Multi-region (Europe + Tokyo) behind CloudFront; disaster recovery with Velero on AWS and Azure; Terraform state in one place.

  3. then

    Deployments move to GitOps: GitHub Actions builds, Argo CD deploys, Image Updater promotes. Production and acceptance per app; onboarding by GitHub topic.

  4. now

    Infrastructure moves to Pulumi in Python with push-based GitOps: policy first, tests, saved plans, review and drift gates, OIDC, self-hosted runners. Plus the logging pipeline and the CLI.

Also running on the platform: metrics and dashboards (Grafana), network observability, an LLM gateway in front of a GPU machine, and MCP servers so AI agents can read the cluster safely.
