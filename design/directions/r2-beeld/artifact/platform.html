Hosting platform

The Kubernetes platform our client projects run on: AWS first, and the same setup on Azure where a client needs it.

Work at Harborn · 2022 to now · I designed and built it, and lead the team that runs it

Every client project used to get its own setup, with its own pipelines, monitoring and way in, so every upgrade and every incident was a one-off. In 2022 I started building one platform instead.

It now runs 8 Kubernetes clusters for Dutch and international clients, on AWS in Ireland and Tokyo and on Azure. The largest runs more than 1,500 pods, and the main cluster has around 80 Argo CD applications.

How it grew

  1. 2022The first standardised cluster: EKS on a dual-stack network across three availability zones, built from Terraform modules, with ready-made modules for Aurora, Redis, OpenSearch, EFS and a bastion. Karpenter adds and removes nodes as load changes, an ingress controller sits behind a Network Load Balancer with fixed IPs, and cert-manager handles certificates. Rancher gives one view of the fleet.
  2. ThenA second region in Tokyo, disaster recovery with Velero on AWS and Azure, and a published end-of-support date for every database, search and ingress version we offer, so upgrades are planned.
  3. ThenDeployments moved to GitOps with Argo CD.
  4. NowInfrastructure is moving from Terraform to Pulumi, behind a pipeline that is the only thing allowed to change production, and logs moved to Loki.

From commit to production

Deployments only go through git. One root application manages every environment, and Argo CD projects keep each team and client inside its own boundaries.

Every app gets two environments. Acceptance follows release candidates and production follows stable release tags; builds from main never deploy. CI builds and tests each release and pushes an immutable image. Argo CD Image Updater watches the registry and commits the new image version to git, and Argo CD syncs it. Argo CD also self-heals drift in the cluster.

A repo that follows our conventions is onboarded by adding a GitHub topic. An ApplicationSet then creates both environments.

Infrastructure changes

Infrastructure is Pulumi in Python, with one state per concern. Every change is a pull request that goes through these steps:

  1. Tests run against the modules, with resource shapes checked using Pulumi mocks.
  2. The preview runs with a mandatory CrossGuard policy pack, so a resource that breaks a rule fails here. The preview is saved as a plan.
  3. Someone other than the author reviews and approves the plan.
  4. The pull request is merged.
  5. The pipeline refreshes the state and checks the apply against the approved plan. Anything destructive that wasn’t in the plan is refused.
  6. The pipeline applies.

The pipeline runs on self-hosted runners in the cluster and gets short-lived cloud roles through GitHub OIDC, so CI holds no cloud keys. The deploy role can only write IAM resources under a name prefix that the pipeline’s own roles don’t match, so it can’t widen its own permissions. The steps are shared composite GitHub Actions, used by every infrastructure repo. A separate daily job reports infrastructure drift to Slack.

To get into an environment we built a small Python CLI: SSO with an admin or read-only role, a shell on the bastion without opening ports, and policy-checked previews. It has no apply.

Logs

Alloy runs on every node and ships every pod’s logs to Loki, which runs with its caches on a dedicated platform node pool. Grafana is where people search them.

The logs are stored in encrypted object storage, and exactly one service account can reach the bucket, through workload identity. Loki’s compactor owns the 90-day retention; the bucket has no lifecycle rules, for the reason in the lessons below.

Europe and Tokyo

The second cluster runs in Tokyo, next to the one in Ireland. CloudFront sits in front of both: its cache behaviours send region-specific paths to the Tokyo origin and everything else to Europe, and static content is served from the edge.

A small CronJob we built keeps chosen Deployments, ConfigMaps and Secrets in Tokyo in step with the main cluster, so changes are still made in one place.

Trade-offs

The syncer for Tokyo predates the move to GitOps. Today I’d replace it with Argo CD ApplicationSets that target both clusters, so git is the only source for both regions.

The move from Terraform to Pulumi is gradual, so for now some infrastructure lives in each, with two sets of modules and conventions until the migration is done.

Lessons

  • Symptom
    Queries over older logs fail or come back incomplete.
    Cause
    A lifecycle rule on the bucket deletes chunks that Loki’s index still points to.
    Fix
    Let Loki’s compactor own retention, and keep lifecycle rules off the log bucket.

Built with Kubernetes (EKS, AKS), Argo CD and Image Updater, Pulumi with CrossGuard, Terraform, Karpenter, GitHub Actions, Loki, Alloy, Grafana, Velero and Rancher.
