Hosting platform

An AWS-first Kubernetes platform for our client projects, with the same setup on Azure where the client lives there.

Role
Designed and built it; I lead the team that runs it
Period
2022 to now
Type
Work, at Harborn

Context

Every client project used to get its own slightly different setup: different pipelines, different monitoring, different ways to get in. That made every upgrade and every incident a one-off.

Since 2022 I’ve built one platform instead, with the same building blocks for every project. A new app starts with production and acceptance environments, TLS, logging and dashboards, without anyone changing the cluster by hand.

How an app gets deployed

Deployments go through git only. Argo CD runs every environment from one root application, and Argo CD projects keep teams and clients inside their own boundaries.

  • Every app gets production and acceptance. Production follows stable release tags, acceptance follows release candidates. Builds from main never deploy.
  • CI builds and tests each release and pushes an immutable image to the registry. Argo CD Image Updater watches the registry and commits the new image version to git; Argo CD then syncs.
  • Onboarding a repo that follows the conventions is adding a GitHub topic. An ApplicationSet creates both environments.

How infrastructure changes reach production

Infrastructure is Pulumi in Python, with one independent state per concern. A change is a pull request, and the pipeline is the only thing that writes to production.

  • Policy first. A CrossGuard policy pack runs as mandatory, so a resource that breaks a rule fails at preview, before anyone reviews it.
  • Tested. The logic lives in importable modules, and resource shapes are tested with Pulumi mocks.
  • Reviewed plan. The preview is saved as a plan, and someone other than the author approves it.
  • Fail-closed drift gate. After merge, apply refreshes against the real state and refuses anything destructive that wasn’t in the approved plan.
  • No static keys. GitHub OIDC gives short-lived cloud roles on self-hosted runners in the cluster. The deploy role can only write IAM resources under a name prefix that can’t match the pipeline roles, so it can’t widen its own permissions.
  • Shared composite GitHub Actions for preview, deploy and drift, used by every infrastructure repo. A daily drift check reports to Slack.

What every cluster is built from

The building blocks started as Terraform modules: AWS first, Azure where the client lives.

  • EKS on a dual-stack (IPv4 and IPv6) network across three availability zones, with Aurora, Redis, OpenSearch, EFS and a bastion as ready-made modules.
  • Karpenter adds and removes nodes as load changes.
  • Traffic comes in through a Network Load Balancer with fixed IPs, then ingress-nginx on every node (proxy protocol, HSTS). cert-manager handles certificates.
  • Rancher gives one view of the whole fleet.
  • Velero backs up cluster resources and volume snapshots on AWS and Azure, and we publish end-of-support dates for every database, search and ingress version we offer.

Logs

Every log line from every pod is searchable in Grafana and stored encrypted.

  • Alloy runs on every node and ships to Loki, which runs with its caches on a dedicated platform node pool.
  • Logs land in encrypted object storage. Loki’s compactor owns the 90-day retention; the bucket has no lifecycle rules (see the lesson below).
  • Exactly one service account can reach the bucket, through workload identity.

Europe and Tokyo

For users in Asia and Oceania, a second cluster runs in Tokyo next to the European one.

  • CloudFront sits in front of both. Its cache behaviours route by path to the regional origin, and static content is served from the edge.
  • A small resource syncer we built (a Kubernetes CronJob) keeps chosen Deployments, ConfigMaps and Secrets in Tokyo in step with the main cluster, so changes are still made in one place.

Operating it

We built a small Python CLI that knows every environment, so getting in doesn’t depend on a wiki page. It deliberately has no apply: only the pipeline changes production.

login

shell
a session on the bastion, without opening ports

a preview of a change, with the policy pack enforced
bootstrap
the foundation for a new environment

The same platform also runs metrics and dashboards in Grafana, network observability, an LLM gateway in front of a GPU machine, and MCP servers that let AI agents read the cluster safely.

How it grew

  1. 2022A first standardised hosting cluster on AWS EKS, built from Terraform modules and managed with Rancher.
  2. ThenTokyo behind CloudFront, disaster recovery with Velero on AWS and Azure, and Terraform state in one place.
  3. ThenDeployments moved to GitOps: GitHub Actions builds, Argo CD deploys, Image Updater promotes.
  4. NowInfrastructure moves to Pulumi with the gated pipeline above, plus the logging pipeline and the CLI.

Trade-offs

  • The resource syncer for Tokyo predates the move to GitOps. Today I’d replace it with Argo CD ApplicationSets that target both clusters, so git is the only source for both regions.
  • The move from Terraform to Pulumi is gradual, so for now some infrastructure lives in each. That means two sets of modules and conventions until the migration is done.

Lessons

  • Symptom
    Queries over older logs fail or come back incomplete.
    Cause
    A lifecycle rule on the bucket deletes chunks that Loki’s index still points to.
    Fix
    Let Loki’s compactor own retention, and keep lifecycle rules off the log bucket.

Principles

  • If I do it twice, I automate it. Onboarding a new app is adding a topic to its repo.
  • Every change goes through a pull request, infrastructure included. The review shows exactly what will change, and merging is the deploy.
  • Guardrails before features. I write the policy that blocks a mistake before I build the thing it protects.
  • Make it easy to run. The platform repairs drift on its own, alerts point to a runbook, and anyone on the team can operate it.
  • Write down why, and teach it. Decision records in every repo, and training sessions with clients.

Stack

Kubernetes (EKS, AKS), Argo CD and Image Updater, Pulumi (Python) with CrossGuard, Terraform, Karpenter, GitHub Actions with OIDC, Loki and Alloy, Grafana, Velero, Rancher, AWS, Azure.
