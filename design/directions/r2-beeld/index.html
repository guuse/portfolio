Experience

I’ve spent my whole career at development agencies, where every client brings a different stack, a different cloud and a different deadline. For the last eight years I’ve worked on the layer underneath: the platform, the pipelines and the security that let many projects ship without each one reinventing them. Today I lead the infra team.

highlight

A standardised, cloud-agnostic Kubernetes hosting platform.

I designed and built the hosting platform our client projects run on. It’s the same setup on every cloud, driven from git, and it now runs 8 clusters, from small to large: the biggest runs more than 1,500 pods. They’re in the Netherlands and abroad, including a cluster in Japan. The focus is automation and scaling: new projects get a namespace, a pipeline and monitoring on day one, and the platform grows without hand work. I also run training programmes with clients, so their own teams can work on it.

    • Helm charts and Kustomize overlays, standardised across projects
    • Upgrades, multi-tenancy, autoscaling and capacity across 8 production clusters

    Git is the source of truth; the cluster follows.

how I work

  1. Boring is a feature. If a platform is exciting to run, something’s wrong.
  2. Everything in git. Infrastructure, config and decisions. If it’s not in a repo, it doesn’t exist.
  3. Automate the second time. Not the first, and certainly not the third.
  4. Write it down. Every repo of mine starts with a context file and decision records.

Homelab platform

A small, production-style Kubernetes platform on an old laptop under the TV.

Live2026

An old laptop with the lid shut runs Proxmox, a single-node k3s cluster and everything I build. It’s managed the way I’d run a client platform: one git repo, Argo CD syncing every app, wildcard TLS, and no open ports. If the disk dies, I rebuild it from the repo in an afternoon.
